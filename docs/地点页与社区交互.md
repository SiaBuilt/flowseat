# 流动工位：地点页与社区交互（2026-10-15）

本次统一围绕“找得到 → 判断值得去 → 到店能开工 → 到访后补充”组织内容，保留极简黑白风格。

## 全局信息结构

| 层级 | 用户判断 | 主要内容 |
| --- | --- | --- |
| 发现页 / 地图 | 去哪一家 | 城市、费用、地点类型、工作区域筛选；卡片展示预算、插座、椅子、网络、近期空位状态；收藏入口 |
| 地点页概览 | 值不值得去 | 名称、片区、类型、收藏、分享；预算与估算依据；空位反馈及时间 |
| 办公条件 | 能不能专注工作 | 插座数量与覆盖、椅子、Wi-Fi、安静 / 讨论 / 独立通话区域 |
| 菜单与消费 | 预计花多少 | 咖啡馆饮品与餐食；工位日票或小时票；商家菜单链接、更新时间与出处 |
| 到访须知 | 怎么进入和停留 | 开放时段、进入方式、停留规则、其他设施；真实地图与导航后续接入 |
| 社区体验 | 别人实际怎么用 | 署名、到访日期、上午 / 下午 / 晚间、实际消费、体验、有帮助 |
| 信息纠错 | 如何处理变化 | 原因选择、日期、依据；编辑已有反馈，重复操作不增加人数 |

## 费用与菜单

免费、需消费、付费工位保持三种独立标签。“免费”仅指空间使用，不推断饮品、停车等都免费。
预算必须带单位和依据，如一人约两小时、一杯饮品，或日票 / 小时价；预估消费不等于最低消费，也不保证商家允许同样停留时间。
菜单优先关联商家允许公开的 HTTPS 链接，保留更新时间。前端已有 `menuUrl` 与 `menuUpdatedAt` 字段和跨端打开适配；没有可靠来源时不编造商家链接。当前四个地点均为虚构，菜单与价格明确标为演示。

## 空位与闭店分别处理

空位为“有空位 / 空位较少 / 已坐满 / 待确认”。用户应在现场反馈，显示观察时间；本版默认一小时失效，后台或商家实时座位系统尚未接入。因此称“近期反馈”，不称实时余座。过期或未来时间均回到待确认。列表与地点页一致。

闭店属于长期可用性变化：一次独立、有依据反馈进入怀疑闭店；两位独立用户提供依据并与公开来源核对后，社区标记闭店、默认隐藏；允许提交重新营业证据恢复。不能把同一个用户点击两次当作两票，也不能把两个来源当两位用户。正式服务需要登录、去重、证据记录和审核权限，前端不可自行完成真实隐藏。

暂时停业、不再接受电脑办公、费用设施错误分别处理。坐满不影响收录状态。当前本机演示只覆盖保存与修改纠错表单，不宣称完成社区判定。

## 社区动作

心形是收藏地点；分享复制可直接进入该地点的链接，保留站点原有访问权限；体验包含到访时段与实际消费，避免先生成没有依据的平均分；“有帮助”用于体验内容，和收藏分开。正式服务再接回复、举报体验与多人统计，当前仅本机体验验证。

本版所有反馈仅设备本地保存，没有真实账号、多用户同步、运营审核或商家实时数据。Wi-Fi 仍是演示连接信息。正式发布真实地点前，应展示信息来源与最近确认时间，并清楚区分商家确认、社区到访和公开资料。

## 参考与取舍

[LaptopFriendly](https://qr.laptopfriendly.co/)将网络、插座、座椅与适合办公的时间放在前面。它承诺地点经过团队实访与手动审核；我们的社区维护模式不沿用这项承诺。

[Airbnb 的举报流程](https://www.airbnb.com/help/article/3598)从价格区域下方进入，再选择原因、补充细节、提交。本版采用类似的渐进表单，避免误触即闭店。社区闭店判断与空位时效是我们的产品规则，并非 Airbnb 规则。

## 验证

Web 与微信小程序构建、TypeScript 检查、14 项测试通过，其中新增两项验证空位过期与未来时间无效。小程序未在真实微信账号环境中验证。浏览器验证菜单、坐满、分步纠错、体验与有帮助的刷新后保存、地点分享链接；另检查手机尺寸布局。
