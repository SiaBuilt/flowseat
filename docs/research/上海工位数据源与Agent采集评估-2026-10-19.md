# 上海工位数据源与 Agent 采集评估

2026-10-19 · FlowSeat / 流动工位 · 第一轮可行性调研

**结论：上海可以做，但首发应由平台先提供一批可决策的地点，再让用户补体验与变化。没有发现任何一家现成数据源能一次提供完整、近期且可直接复用的工位档案。**

地图继续选腾讯，理由是小程序显示与基础位置服务适配；这不代表腾讯拥有最完整的办公条件。商家官网、场馆公告和商家确认应成为第五类核心来源。电话 Agent 值得试验，但不能作为首发唯一的数据生产方式。

## 1. 这次实际做了什么

- 选取上海 10 个目的性样本：4 个咖啡／复合空间线索、2 个联合办公、2 个社区公共空间、2 个图书馆。不是随机样本，不代表全上海；未覆盖自习室，下一轮必须补充。
- 使用项目方提供的腾讯 Key，实际调用 21 次接口：10 次地点搜索、9 次首候选附近停车场搜索、2 次别名补查。每次最多返回 3 条。
- 阅读腾讯、高德、美团／点评的官方接口说明，检索点评、小红书的公开网页；另核对经营方官网、上海政府和图书馆公开页面。
- 腾讯完成真实接口测试；高德仅完成文档和 2 个公开地点页面核对，未使用高德 API；点评没有合作接口权限，小红书没有笔记检索接口权限。本轮未取得可用于同样本计数的两平台原始评论／笔记集合。
- 没有拨打电话、没有实访、没有发布地点，也没有把商家宣传当成用户实测。

**因此，本轮可以判断数据生产路径与缺口；不能诚实地给出“四个平台上海覆盖率排名”。检索不到公开网页，也不等于该平台 App 里没有信息。**

## 3. 四类平台，谁的信息更全

**“内容可能丰富”与“可作为自动化稳定数据源”是两项不同的评分。** 下面是能力和适用性判断，不是未完成的覆盖率实验。

| 数据源 | 最有用的信息 | 深度办公信息的局限 | 本项目接入结论 |
|---|---|---|---|
| 腾讯地图／位置服务 | 地点身份、地址坐标、电话、周边停车候选；与小程序地图衔接 | 本次搜索没有插座、松紧、舒适度等字段；营业时间等也不能保证由搜索接口返回 | 第一位置底座；仅按实际返回与许可范围使用，不承担完整办公档案 |
| 高德地图 | POI、入口、周边搜索；官方 v3 文档有停车类型，POI 2.0 有商业信息等扩展字段 | 接口版本、权限和字段填充不同；没有看到插座松紧的标准字段；未完成本项目 API 同样本比较 | 第二位置源的候选。先比较新增有效信息和授权成本，再决定接入 |
| 大众点评 | 商户聚合、人均消费、环境评价、营业时间、评论线索；合作文档存在停车筛选 | 环境评分不等于安静办公；人均消费不等于最低消费。接口需要合作身份，不能假定全部评论自由获取 | 如果取得授权，优先用于咖啡馆消费与环境线索；当前不能作为保证可调用的数据源 |
| 小红书 | 适合发现“能带电脑”“靠墙有插座”“某时段吵”等场景线索（待同样本实证） | 内容非结构化、分店与日期容易混淆；本轮未获得可计数原始笔记集合，也未确认通用笔记检索 API | 作为发现线索与用户主动提交来源入口；不把未授权全站采集设为基础设施 |
| 商家／场馆官方资料（新增） | 允许办公、入场／预约条件、工位产品、设施、停车入口与优惠规则 | 商家有宣传偏向；不会可靠给出插座松紧、当前噪声与个人久坐感受 | 核验经营规则的优先来源，值得主动建设商家确认入口 |

**我的选型判断：腾讯负责地图；商家与场馆资料负责经营规则；点评是咖啡馆深度信息的优先评估对象；小红书负责发现有价值的线索。尚没有证据支持把其中任何一家宣布为“最全”。**

点评合作文档列有环境评分、营业时间、均价、停车筛选和评论接口，但要求平台分配的企业 ID，不能把文档存在当作我们已获访问权。[美团企业版接口](https://h5.dianping.com/app/bep-docs/sky-doc/canyinopenapi/daocan_api.html)

腾讯文档支持周边搜索和子地点；高德 v3 与 2.0 字段不同，不能拼接成一套承诺所有门店必有的字段。[腾讯搜索](https://lbs.qq.com/service/webService/webServiceGuide/search/webServiceSearch) · [高德 v3](https://lbs.amap.com/api/webservice/guide/api/search/) · [高德 POI 2.0](https://lbs.amap.com/api/webservice/guide/api-advanced/newpoisearch)

小红书公开开放平台与账号 API 文档不能证明已提供本项目所需的全站笔记检索／评论授权。[开放平台](https://open.xiaohongshu.com/) · [账号 API](https://openaccount.xiaohongshu.com/docs/api-reference)

### 必须反对的几个推断

- “地图有这个点”不能证明它营业、允许电脑或接待临时访客。
- “高分、环境好、照片漂亮”不能推出安静、桌面合适、久坐舒服。
- “有插座”不能推出每个座位可充电；总插孔数也不等于可充电座位数。
- “有停车场”不能推出公众能停，更不能推出免费或当前有余位。
- API 能调用不等于取得任意长期存储、转售、跨平台混用或图片评论再发布权。按服务授权和具体用途核实；短期研究通过不等于商业上线已获许可。
- 一篇文章被多个平台转载，仍然只算一份证据；搜索结果摘要和 AI 聚合文章不作为关键结论唯一证据。

## 4. 应该定义哪些字段

先统一 20 个静态／半静态决策字段，以便计算覆盖率；不靠拆分经纬度等简单字段把“完整度”做高。

| 组别 | 字段 | 首选生产方式 |
|---|---|---|
| 基础 6 项 | 精确分店身份、地址与入口、坐标、开放时间、公开联系渠道、场所类型 | 地图＋官方来源；冲突复核 |
| 使用条件 6 项 | 允许电脑办公、电脑＋鼠标桌面、费用模式、停留／预约限制、插座数量档位或覆盖、Wi-Fi 可用性 | 官网／商家确认；用户补充验证 |
| 体验 4 项 | 座椅久坐感受、分时段噪声、安静／讨论／通话区域、供电稳定／插座松动问题 | 用户到访或付费体验贡献；商家只能提供部分客观条件 |
| 停车 4 项 | 停车设施与入口、访客开放条件、收费规则、到店步行路线 | 地图候选＋物业／经营方资料＋用户纠错 |

“是否免费”与“预计总支出”分开。驾车用户的预算 = 办公／消费费用 + 对应停留时长停车费用；缺一项则显示部分预算和缺项，不能默认 0 元。

插座数量采用 0、1—5、6—10、10 个以上、未知；另记录覆盖区域、可充电座位比例／描述和统计口径。不要把“10 个插孔”直接展示成“10 个工位可充电”。

插座松紧改为用户能回答的“充电时是否容易掉电／插头松动”，附区域与到访日期；不形成全店电气安全认证。椅子分开记录客观类型、是否靠背／软垫和个人久坐感受；软不等于适合久坐。

噪声按工作日／周末、上午／下午／晚间记录；不要求普通用户凭空填分贝。三类工作区域可放同一视觉模块，但底层分别记录，避免“有讨论区”误解为“全店可打电话”。

当前坐满、即时网络质量、停车余位独立为动态数据，不进入上述 20 项覆盖率。座位反馈沿用 1 小时失效；停车余位必须有实时运营方数据才承诺实时，不能靠前一天电话。

## 5. 平台与用户贡献的比例

**以下为试验目标和经营假设，绝非本轮已经测得的上海比例。** 分母固定为“选定首发地点 × 20 个字段”，只计算有来源、适用范围和有效日期的非未知字段；同时另外计算核心条件达标的地点数。

| 阶段 | 平台整理／核实 | 用户到访贡献 | 保持未知 | 含义 |
|---|---:|---:|---:|---|
| 只有地图＋可用公开资料（假设基线） | 45%—60% | 0% | 40%—55% | 需要用后续 30 店审计验证，不是现有统计 |
| 商家确认后、首批发布目标 | 70% | 0% | 30% | 典型目标为 20 项中平台准备 14 项；达到门槛的地点才进精选库 |
| 初步共创后的目标情景 | 70% | 20% | 10% | 用户新增 4 项，2 项仍未知；不强求每店满字段 |

两项关键纪律：同一字段不能同时算平台和用户新增；用户复核已有值计入“验证次数”，不重复增加完整度。即时信息不套用 70/20/10。

首批地点必须确认：允许电脑办公、桌面能容纳电脑与鼠标、入场／费用规则、开放时间。插座状态必须明确呈现；无电源但允许办公可保留，用户筛选决定。未知关键准入条件的地点进入“待核实线索”，不混入推荐列表。

**70% 是平台先把价值做出来的责任分配目标，不是 Agent 能保证自动完成 70% 的能力承诺。** 如果合法可用来源和商家确认仍不能填到核心门槛，应缩小首发范围，或为少量现场验证支付内容成本，不能靠生成补齐。

## 6. 电话 Agent 能补什么，不能补什么

适合询问：是否接待电脑办公、消费与停留规则、插座大致档位、可充电区域、Wi-Fi 是否提供、是否有电话间、访客停车入口与优惠条件。

不适合承诺：插座松紧的独立验证、所有座位舒适度、各时段噪声、未来空位。店员可能不知道停车收费，需转物业／停车运营方；店员说“没问题”只记为商家自述，不覆盖反向到访证据。

**首轮一次只问最缺的 3—5 项，目标 2—3 分钟，不能要求一通电话填完所有深度信息。** 先问是否允许电脑办公；若拒绝或已停业，结束后复核状态，避免继续长问。复杂费率、照片和座位分布转商家确认表。

建议开场：“您好，我是流动工位的信息核实 AI 助手，我们在整理上海适合带电脑工作的地点。方便花两分钟核实几项公开服务信息吗？您不方便的话我们就不打扰了。”说明是否转写／录音及用途，并按实际线路与服务要求取得对应同意；不冒充顾客、不承诺到店、不安排虚假预约。

任务状态：待核实 → 资格与联络检查 → 排队 → 接通／未接通／拒绝 → 提取字段 → 逐项复述确认 → 商家自述待审 → 公开。拒绝后停止联系；不把未接通判闭店。试点重试上限建议每店本轮一次，时段按场地方作息安排，不密集重拨。

### 当前技术与准入判断

- 腾讯云联络中心公开了单次 AI 通话、自动外呼任务及话后标签接口，因此技术路径存在；但本项目的主体、线路与调查场景是否获准尚未验证。[腾讯官方 API](https://cloud.tencent.com.cn/document/product/679/47724)
- 阿里云官方企业资质文档明确：个人用户不支持语音服务及智能外呼机器人，且列出若干不支持的主体类型。项目目前只有个人身份，因此不能直接把该服务排成可用依赖。[阿里云准入](https://help.aliyun.com/zh/vms/user-guide/enterprise-qualification-management)
- Twilio 等海外语音服务证明可编程外呼可行，但并不证明上海号码的线路、准入、接通率和费用适合本项目；不作为默认绕行方案。[Twilio Voice](https://www.twilio.com/docs/voice/api?save_locale=en)

首发替代方案：Agent 生成已填好来源的确认表，商家自助修改；少量经授权的运营人员／合作方电话核实，Agent 做转写与结构化。创始人不必实访，但不能把“无人愿意核实”当作技术能消除的条件。

本轮只规划外呼，不申请付费线路、不采购服务、不对外发起联系。

## 7. Agent 深度聚合的实际工作流

1. **发现候选**：腾讯地点搜索、经营方官网、场馆公告、允许使用的公开线索、用户主动提交链接。每个连接器声明可读范围、缓存期限、可展示字段和来源条件。
2. **确认是同一分店**：名称标准化只做辅助；联合街道门牌、楼层、坐标和电话。商场内同址店、总馆分馆、相邻入口和品牌更名不能自动合并。低确定性进入现有账号审核队列。
3. **按字段提取证据**：输出结构化候选值、来源 URL、来源日期、抓取日期、实际观察日期、分店／区域／时段、证据类型。模型不得从“装修高级”推出舒适，从“有人用电脑的照片”推出经营方允许全天办公。
4. **检测缺项和冲突**：同源转载去重；高影响字段优先核实。官方规则、商家自述、用户体验并列保存，不能一律用“最新”压掉其他来源。
5. **选择补全渠道**：有官方页面先读取；需要商家确认则生成确认表／电话任务；插座松动、久坐、时段噪声生成现场微任务。
6. **审核后发布**：首次地点准入与冲突字段由指定账号快速审核；后续低风险、同源、格式化更新才逐步自动化。没有完整证据就显示未知。
7. **按变化速度复核**：预算、时段、停留政策拟 30 天复核，静态设施拟 90 天；节假日与争议触发即时任务。上述周期为产品初值，按真实变化率调整。采集频率不能超过来源授权。

排序任务的依据是“被查询／收藏的次数 × 缺失字段对决策的影响 × 过期程度 ÷ 核实成本”。先解决被真实用户需要的店，不每天扫描整个上海。

## 8. 停车信息要单独做一层

每处工位关联少量停车设施，而不是把地图返回的第一个点当作答案：

- `parking_facility` 记录设施身份、公共／内部／未知、车行入口、步行出口、开放时间、来源与确认日期。
- `parking_tariff` 记录计费周期、首时段、后续单价、封顶、免费时段与消费抵扣条件，支持无法结构化时保留简短规则和来源。
- `place_parking_link` 记录与门店关系、直线距离、实际步行路线距离及候选／已核实状态；车行入口与人行出口分开。
- 同一设施的地上／地下、入口 POI 和停车场主体进行人工可撤销的合并。内部停车、访客不明、来源过期默认不进入“已确认可停”筛选。

第一版先交付“附近停车候选＋入口导航＋权限／费用待确认”，核实后升级为推荐停车。地图没有实时余位时，明确显示“余位未知”。

## 9. 技术实现路径

保留 uni-app Vue 3 前端与现有账号内审核入口。数据采集服务与地图 UI 分开；新增采集逻辑通过接口接入，避免将来换微信后端时重写采集流程。

### 数据层

新增设计表：`source_documents`、`place_external_ids`、`field_observations`、`field_resolutions`、`verification_tasks`、`merchant_confirmations`、`parking_facilities`、`place_parking_links`、`call_attempts`、`contact_suppression`。这是待实现设计，本轮不生成或应用数据库迁移。

每条字段观察至少包含：`place_id / field / value / unit / scope / source_type / source_ref / source_published_at / observed_at / fetched_at / valid_until / review_state / evidence_strength / supersedes_id`。不保存 Key、私人联系方式或未经允许的评论全文；原始录音如确需保存，另设权限与删除期限，默认不公开。

证据状态采用“来源陈述／商家确认／用户体验／冲突／过期”，不展示未经校准的 97% 之类模型置信度。解析置信与事实可信分开，地点匹配状态也单列。

### 服务层

- `LocationProvider`：搜索、地理编码、附近停车、路线；先腾讯，后续高德适配器可替换。不同来源数据可否混用须按具体许可确认。
- `SourceConnector`：只读取获准来源，限频、缓存、记录版本；登录墙／未获授权的内容进入人工来源入口。
- `EvidenceExtractor`：模型结构化提取＋字段白名单＋证据检查；没有证据的字段输出 unknown。
- `ResolutionService`：合并去重、冲突保留、过期判断、发布门槛。
- `VerificationQueue`：任务优先级、幂等 ID、有限重试、费用预算和失败原因；不在用户打开地图时同步做全网搜索。
- `CallProvider`：外呼适配器＋供应商管理通话；签名回调、重复事件去重、拒绝名单、转写字段校验和审核。语音会话使用服务商实时能力，现有 HTTP 网站服务接收任务与结果。

当前网站托管身份不能直接当成微信身份。正式小程序阶段单独完成 `wx.login → 服务端换码 → 账号映射` 和上线条件；数据采集层保持服务端接口，不依赖某一种前端登录。地图 Key 已配置到托管环境并通过校验和地址解析，页面真实地图联调／部署尚未完成。

## 10. 起量、成本和反对意见

**如果第一批核心条件靠用户填，起量会明显受影响。** 用户来找地点，却先被要求做调查；没有好地点，就没有到访；没有到访，又没有体验数据。平台必须先承担基础内容成本。

建议从 3 个相邻生活／工作片区做 30—50 个可用地点的目标试验，例如静安寺—南京西路、江苏路—愚园路、衡山路—徐家汇；这只是需求验证候选，不是已经证明的最佳选区。免费／低消费地点要有足够选择，避免因为联合办公官网资料容易获得，最后做成付费工位黄页。

初始候选池可设 80—100 条作为实验目标，筛选到 30—50 条；转化率必须实测。先从有明确办公产品、公开设施说明、愿意确认的商家做起，公共空间逐一确认开放资格。若只有 15 家合格，就发布一个覆盖清楚的小区域，不用未核实地点凑 50。

### 单位经济与电话效果

有效门店数 = 呼叫尝试数 × 接通率 × 愿意回答率 × 信息达标率。作为敏感性例子，100 次首次尝试 × 65% × 50% × 80% = 26 家；这些概率是演算假设，没有进行电话实测。

每家有效门店成本 =（线路／通话费＋语音／模型费＋资料整理与审核人工＋授权固定成本分摊＋复核维护）÷ 新增达标门店数。不能用“每分钟几毛钱”代表完整获客和维护成本。收费、接通率和拒接率都要在小试后测量。

按当前个人主体条件，电话自动化甚至可能先被准入卡住。别为了尚未验证的电话需求先购年费系统；先用商家确认表和少量有预算的内容合作验证“有人愿意回答、回答有用”。

### 主要反对意见与应对

| 反对意见 | 对业务的影响 | 处理方式 |
|---|---|---|
| 店员会把环境说得更好 | 商家自述不能替代体验 | 规则听经营方，体验保留用户视角；冲突并列 |
| 免费空间不欢迎被大规模引流 | 规则变化、公共资源被占用 | 核验开放对象和长时办公许可，避免宣传成无限免费工位 |
| 插座松紧过于细碎、变化快 | 采集贵，覆盖率永远难满 | 做局部问题反馈，带时间和区域，不做全店准入必填 |
| 社区活跃度低，动态信息很快过期 | “实时空位”容易名不副实 | 小范围集中密度；保留短期反馈，过期归未知 |
| 贡献署名不足以驱动陌生人劳动 | 第一批内容生产仍需投入 | 预填、只问 1—2 项、先给用户选择价值；必要时付费种子贡献 |
| 数据授权或 API 成本不适合个人创业 | 全网聚合方案可能落空 | 多来源分层、商家自有资料、用户直接贡献；不以绕过访问限制为方案 |
| Agent 抽取错分店、把旧文当现况 | 白跑损害信任 | 分店匹配、日期、关键门槛审核；保留错误回溯 |
| 19.99 买断而数据要持续维护 | 长期服务成本与一次性收入错配 | 当前免费验证；未来明确城市／版本／维护范围，再验证定价 |
| 只剩泛用地图信息 | 用户没有换产品的理由 | 核心指标是“能否放心去工作”，不是收录地点总量 |

下一轮优先指标：核心条件达标地点数、最近 30 天规则证据覆盖率、分店误合并率、停车误导率、到访白跑率、每个有效新增字段成本、每家月维护工时。不能把收藏量或地图点数当作唯一成功标准。

## 11. 后续怎么把这次评估做成可比较的实验

扩展到 30 个预先固定的上海样本，覆盖 12 咖啡馆、6 联合办公、6 公共／图书馆、6 自习室，记录分店地址。各来源用同一 20 字段、同一近期标准和相同人工查阅时间预算；缺访问权限写“无法测量”，不算信息不存在。

对腾讯、高德分别测真实 API；点评在合作授权或允许的人工界面范围内核查；小红书由合法可访问原始笔记或用户主动提供链接进入。记录“找到了／可结构化／获准使用／近期有效”四个计数，不能混成一个覆盖率。若拿不到授权，本身就是产品接入结果，不继续假设未来必然解决。

以 10 家商家确认和少量愿意参与的用户到访交叉验证抽取结果，再决定电话 Agent 是否值得规模化。不要让创始人自己实访成为唯一流程。
